## 2. 直達查詢結果依目的地整理

**問題**：昨天的直達查詢（`07_direct_reach.sql`）結果是 1,010 列「子路線方向 × 下車站」，同一個目的地重複出現很多次。使用者想看的是「能去哪裡」，要改成一個目的地一列。

**參考**：CLAUDE.md 的資料特性：同一路線號碼可能有多個子路線；合併站牌要用 `station_id`，不能用站名。

**行動**：新增 `sql/practice/08_destinations.sql`，用 `WITH` 接三層暫時表，分兩次 `GROUP BY`：

```
reach      1,010 列   子路線方向 × 下車站（07 的結果）
   ↓ GROUP BY 站位 + 路線號碼，取 MIN(站數)      ← 同一路線號碼的子路線去重
per_route    873 列   路線號碼 × 下車站位
   ↓ GROUP BY 站位，COUNT、string_agg
最終         375 列   一個下車站位一列
```

**結果**：

- 銘傳大學：`109(27), 606(30), 606通勤(30)`，與 Q3 答案一致。
- 市民小巴5 有兩個子路線都到景美國小(景文)，分別是 12 站和 17 站，去重後只留 12 站。
- 「捷運萬芳醫院站」出現兩列，兩個 `station_id` 的路線完全不同，證實分組要用 `station_id`。是否在畫面上合併同名站，留到地標對應時再決定。

另外把 00～08 的重點整理到 backend 的 `sql/practice/README.md`：表的關係圖、每課的新語法與驗證數字、執行順序、三種去重方式、不會報錯的陷阱。

## 3. 直達查詢寫成 Python 函式

**問題**：API 和之後的 LLM function calling 都需要呼叫直達查詢，要把 SQL 包成函式。

**行動**：新增 backend 的 `app/reach.py`，`direct_reach(conn, lng, lat, radius_m=300)` 回傳每個可直達的站位。和 08 的差別：

| 地方 | 08 | `direct_reach` | 原因 |
| --- | --- | --- | --- |
| 起點 | 寫死的經緯度 | `%(lng)s` 等參數，由 Python 傳入 | 任何起點都能查；參數化也避免 SQL injection |
| 路線去重 | `GROUP BY` + `MIN` | `DISTINCT ON (down_station, route_name)` | 除了最少站數，還要留下「從哪站上車、哪個方向」 |
| 路線清單 | `string_agg` 串成字串 | `json_agg` | Python 直接拿到 list |
| 座標 | 無 | 同站位的站牌取平均 | 前端要標點；237 個站位內的站牌座標不完全相同，最多差 91 m |

**結果**：`uv run python -m app.reach` 得到 375 個站位，銘傳大學、景美國小(景文)的結果與 08 一致。

## 學到的觀念

**三種去重方式**

| 語法 | 做什麼 | 什麼時候用 |
| --- | --- | --- |
| `DISTINCT` | 刪掉 SELECT 欄位完全一樣的列 | 只要知道「有哪些」 |
| `DISTINCT ON (欄位)` | 每組挑一列，保留整列 | 要留下某一列本身，例如最近的上車站 |
| `GROUP BY` | 每組合併成一列，其他欄位用彙總函式 | 要統計，例如最小值、數量、串字串 |

**SQL 的執行順序**：`FROM + JOIN → WHERE → GROUP BY → SELECT → ORDER BY`。所以 `SELECT` 裡用 `AS` 取的名字不能用在 `WHERE`；`DISTINCT ON` 在所有 JOIN 之後才執行，「先選上車站、再找下游」才需要用 `WITH` 分成兩段。

**`WITH` 暫時表的欄位，就是它 `SELECT` 出來的名字**，包括 `AS` 改過的名字。括號裡的表別名，外面看不到。
